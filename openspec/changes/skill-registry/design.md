## Context

See proposal. Related: `agent-config` (skills metadata only at start, reads scoped to the agent's skills),
`company-self-service` (stored catalog, D5 operator-only skill contents), `runtime-drivers` 2.3 (node
materialization verified by `skills.Hash`), `core-owned-project-data` (`internal/blobstore`, company-scoped
digests), `node-identity` (signed node requests; a node serves one company), `company-teams` (teams), `user-accounts`
(company per request, roles), `team-builder` (presets reference built-in skills).

Nodes are the users' machines (later virtual machines such as Fly Sprites); no agent runs on our hosts. A node
serves one company and every team of it.

## Decisions (owner 2026-11-03)

### D1. Formats: existing standards, no own manifest
A skill is an Agent Skills directory (agentskills.io): `<name>/SKILL.md` with frontmatter `name` (equal to the
directory, `[a-z0-9-]`, ≤ 64), `description` (≤ 1024), optional `license`, `compatibility`, `metadata`
(string map), `allowed-tools`; supporting files in `scripts/`, `references/`, `assets/`. Categories for discovery
come from `metadata.categories` (comma separated), else `metadata.tags`. No Factory-specific manifest is required.
Our default skills live in a repository in the same format.

### D2. Core owns skill contents
Every indexed skill version is a tar of its directory stored in `internal/blobstore` under the key `skills.Hash`
(the hash nodes already verify). Built-in skills are stored once under the reserved scope `factory`; a company's
own under its company. Core reads (`factory_skills_read`, owner UI) serve the blob, not disk. Removed (no
migration, not released): `path:` entries in `skills.yaml` and the node's disk registry (`skills_root`).

### D3. Sources and fetching
`skill_sources (company_id, id, kind builtin|git|upload, url, ref, subpath, access public|node, update
pinned|track, commit, synced_at, status, error)`.
- **Public git** (`access: public`): Core fetches: `https` only, public addresses only (no private/link-local IPs),
  shallow (`--depth 1`), no submodules, no LFS, hooks disabled, time and size limits, in a fresh directory.
- **Private git** (`access: node`): Core creates a sync job for an online node of the company; the node fetches
  with its own git access (the user's machine, as it clones project repositories), packs the tree at the resolved
  commit (same limits, no symlinks) and uploads it with a signed request (`node-identity`). Without an online node
  the sync waits and the source shows why.
- **Upload**: an owner or admin uploads an archive or a folder in the UI; re-upload updates it.
Core keeps no git credentials. Core-held access (deploy key generated by Core, GitHub App) may come later as an
attribute of a source, never as a run secret.

### D4. The indexer
Over a fetched or uploaded tree, deterministic (the same tree gives the same index and hashes):
1. Discover (first match wins): `.claude-plugin/marketplace.json` → its plugins' skill directories (plugin `skills`
   field, default `skills/`); else `skills/*/SKILL.md`, `.claude/skills/*/SKILL.md`, `.agents/skills/*/SKILL.md`;
   else `SKILL.md` at the root (or `subpath`): a single-skill source.
2. Validate each with today's rules (frontmatter, name = directory, regular files only, no symlinks, ≤ 512 files,
   ≤ 1 MiB each, ≤ 16 MiB total); an invalid skill is a per-skill error, the others are indexed.
3. Hash, store the blob, write `skill_index (company_id, source_id, name, commit, hash, description, categories,
   frontmatter, files)`.
Search is substring/full-text over name, description and categories. The built-in source is indexed by Core at
start from the release's default skills.

### D5. Installed skills live in the catalog
```yaml
sources:
  acme: {git: https://github.com/acme/agent-skills, ref: main, access: node, update: pinned}
skills:
  openspec:    {source: factory, hash: sha256:…}
  brand-voice: {source: acme, commit: 3f2a…, hash: sha256:…, scope: team:saas}
```
Description and categories come from the index (overridable). The loader resolves a skill by its hash in the blob
store. Saving, history and rollback of catalog versions therefore cover skills. A skill name is unique per company
(Claude materializes `.claude/skills/<name>` and the name must equal the directory); a conflict between sources is
resolved by choosing which to install. No `source/name` namespaces.

### D6. Managed once, picked in the agent form
Sources are added, synced and removed on the company's Skills page (and API/CLI) by owners and admins, once per
company, for every team. Installing a skill writes `skills.yaml`. The agent editor offers installed skills
available to the agent's team (Factory and the company's own), with a link to the Skills page; it accepts no URL.

### D7. Updates
A sync of a `pinned` source shows available updates (new hash, file diff); installing one saves a catalog
version. A `track` source installs new hashes on sync automatically (a catalog version authored `sync`). Running
runs keep their pinned `skill_hashes`.

### D8. Delivery to nodes: store plus per-run view
Core pins `skill_hashes` in the run snapshot (exists). `GET /skills/blobs/{hash}`, a node request signed with the
node's key (`node-identity`) and naming the run, serves only hashes pinned on that run of the node. The node keeps
`~/.app-factory/skills/store/sha256-<hex>/` (read-only, immutable): a missing hash is downloaded to `tmp/`,
unpacked, verified with `skills.Hash`, then renamed into the store. Each run gets a view with only its agent's
skills (`~/.app-factory/runs/<run>/skills/<name>`); the drivers install from it (Claude: `<cwd>/.claude/skills/<name>`
with `.factory-skill` and per-worktree excludes, as today; Codex: from the same view). The user's own
`~/.claude/skills` is never touched. GC removes store entries unused for N days and not pinned by an active run.

### D9. Scope
An installed skill may carry `scope: team:<name>` (only agents of that team may include or discover it) or
`scope: agent:<name>` (only that agent). Loading fails when an agent includes a skill outside its scope.

## Risks / Trade-offs

- Fetching user-provided URLs from Core: SSRF and resource abuse are contained by D3's limits; git runs as a
  subprocess without hooks.
- Private sources need an online node to sync; installed skills keep working from Core's blobs meanwhile.
- Skill content is untrusted prompt and script material of the client and runs on the client's own nodes under the
  agent's policies. Built-in skills are ours.
- Core storage grows with skill versions; blobs are deduplicated by hash and old unreferenced versions can be
  collected later.
